What I’d actually delegate to a browser agent

A practical receipt workflow: where browser access helps, what belongs in code, and how to judge whether delegation saved any work.

Raghav Maini · September 12, 2026

The browser workflow I’d try first is collecting receipts from merchant portals and matching them to a statement. I’d want the original documents, a reconciled file, and a short list of exceptions. That gives me a specific job to evaluate, with a result I can check.

The tools are starting to fit that job. OpenAI’s July 9 introduction of ChatGPT Work combines work across apps and files with a built-in browser. For this example, that means accessing the portal, obtaining the material, then working on the files. The announcement establishes those capabilities; it doesn’t tell us whether a particular reconciliation will save time.

I would split the job into document collection, extraction, matching, and review. Each needs a different interface and a different definition of done.

First, though, I’d check whether existing accounting software already imports those receipts. The agent earns its place where unsupported merchant portals leave collection work behind. A working integration is a reason to leave that part alone.

Get the documents, then leave the interface

For the acquisition step, I’d start with a supported export or an authorized API if one exists. Otherwise, the browser earns its place: navigate the account, choose the period, and download the receipts. Copying visible rows from a table is a poor substitute when the site offers the complete file. Pagination and filters can make a convincing-looking extract incomplete.

The handoff matters. Each downloaded file should retain its merchant, account, covered period, and source location. A filename alone doesn’t establish that it belongs to the account the user meant. If the portal doesn’t provide a stable document URL, preserve the document identifier and enough account context to find it again.

How I’d divide the receipt workflow
Part of the jobInterfaceWhat must survive the handoff
Obtain receiptsAuthorized export/API, or browser controlsOriginal files, account and period
Extract fieldsDocument parser or OCR, as neededOriginal document and page for each value
Match and reconcileCode over the downloaded filesSource row IDs, matching rules, exceptions
Resolve ambiguitySource document or portal, then human reviewThe conflicting evidence and the unresolved question

A downloaded receipt may be a PDF or image. Before matching anything, I’d extract its fields and retain the source document and page beside each value. An unclear amount or missing currency belongs in the exception list. Reproducible arithmetic can still produce a perfectly consistent answer from a misread receipt.

Arithmetic, grouping and duplicate checks then belong in code, with original statement rows preserved. A shared transaction reference is useful only when both records actually contain it. Otherwise, amount, date and merchant can suggest a match; repeated charges and refunds may leave several candidates. I’d keep those unresolved rather than let a plausible match silently become an accepted one.

The web is starting to offer another route

WebMCP gives site owners a way to help. Chrome’s documentation, updated August 7, describes a proposed standard for exposing JavaScript operations and annotated HTML forms as structured agent tools. The site declares an operation and its inputs, saving the agent from inferring them from controls on a screen.

If I owned the portal, I’d consider export_receipts, taking an account and period and returning document references. The contract must distinguish starting an export from returning completed files; the agent’s next action depends on which has happened.

André Cipriani Bandarra’s August 26 design guide makes a useful point about failures: the response should explain the missing prerequisite or invalid state. For this portal, “select an account before exporting” gives the agent a recoverable next step. “Export failed” leaves it guessing.

Chrome offers WebMCP through an origin trial, and sites must implement their tools. It primarily serves local browser workflows with a human involved. I wouldn’t make an unattended service depend on universal support. Existing APIs and exports remain useful; browser interaction fills the gaps.

Test the handoffs, not just the happy path

Alibaba’s August 18 Wuying-Browser-Agent paper describes a browser system that primarily reads structured page content, requesting screenshots when visual grounding is needed. Its context is reconstructed as the browser changes, rather than treated as an indefinitely growing transcript. That distinction is practical: an element reference from an earlier page is not an enduring fact about the task.

In the receipt workflow, I’d keep “this document belongs to this account” separately from “the download button is this element.” After navigation, the latter needs a fresh observation. Throwing more history at the model doesn’t make an obsolete reference valid.

The July revision of WeaveBench examines deliberately mixed-interface tasks in controlled environments. Its evaluators recheck files, images and execution evidence because plausible final artifacts can conceal fabricated work. For this workflow, I’d inspect the transitions: did the downloaded receipt produce the extracted value that the matching code actually used?

For a pilot, I’d use real historical statements and receipts whose matches I can check. Measure missing documents, incorrect matches, unresolved cases, and the time I spend reviewing or rescuing the run. Compare that with doing the same work manually. A fast agent that leaves me reopening every portal has failed the business test.

I’d start with document collection and reconciliation because the originals let me inspect the result. Changes to payments or accounts would be a separate workflow. What would earn broader delegation is fewer missing documents and incorrect matches, with less review time on comparable batches.
